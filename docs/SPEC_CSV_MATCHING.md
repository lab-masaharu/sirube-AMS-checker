## 0. この方式に至った経緯（なぜ方針転換したか）

### 旧方式とその廃止
当初は、ふれんず物件詳細ページを Playwright で自動スクレイピングし、
状態・価格を取得する MCP サーバー（`FreinsAdapter` + `freins-server.js`）を実装していた。
PC↔VPS の SSH 逆トンネル経由で VPS の n8n から呼ぶ構成まで動作実証済みだった。

**しかし、ふれんずの規約に、機械による自動スクレイピングが抵触する。**
技術的に動作しても、規約上使用できない。したがって旧方式（自動スクレイピング）は**不採用**とする。

- 旧方式の資産（`FreinsAdapter.js` / `freins-server.js` / `scripts/tunnel-keepalive.ps1` 等）は
  削除せず、「規約により不採用」と記録した上で Git 履歴に残す（なぜ廃止したかを後から追えるように）。

### 新方式の核心
**ふれんずへのアクセスとCSVダウンロードは営業本人が手動で行う（＝人間による正規利用）。
その後の社内処理（AMS突合）だけを自動化する。**

- ふれんずへの機械アクセスは一切行わない。規約に抵触しない。
- 営業の自然な操作（検索してCSVダウンロード）が、そのまま処理の起点になる。
- スクレイピングの苦労（1件ずつ巡回・アクセス制限回避・トンネル維持）が丸ごと不要になる。
- 制約が、結果的にシンプルで壊れにくい設計を生んだ。

## 1. 全体フロー

```
営業PC
  ↓ ふれんずで検索（エリア・種目・価格帯など任意条件）
  ↓ CSVダウンロード（★ふれんず側の制限で最大200件/回）
  ↓ 専用フォルダへ保存
  ↓ フォルダ監視 → n8n の Webhook へ送信
n8n
  ↓ CSV受信・パース
  ↓ AMSデータと突合（照合MCPサーバーを呼ぶ）
  ↓ 変更候補一覧を作成
  ↓ 結果を営業本人のメールへ送信
営業
  ↓ メールで確認 → ふれんずURLで現物確認 → 必要ならAMS更新を依頼
```

### 200件制限の運用回避
- ふれんずCSVは1回あたり最大200件。全件は一度に取れない。
- 営業は検索条件を変えて複数回ダウンロードすればよい
  （例:「春日市の土地」で200件 →「大野城市の戸建」で別の200件）。
- **営業がダウンロードする範囲＝営業が実際に気にしている範囲**なので、
  全県全物件を網羅する巨大な仕組みは不要。営業の関心と照合範囲が自然に一致する。
- n8n の発火は「営業各自のダウンロード（＝照合してほしいという意思表示）」を監視して行う。

## 2. 照合の鍵：物件番号では繋がらない（重要）

### 発見した事実
ふれんず物件詳細ページ・CSV・AMS を突き合わせた結果、番号体系が3種あることが判明した。

| 番号 | 桁・例 | 出所 |
| ---- | ------ | ---- |
| ふれんず物件番号 | 8桁 `99850307` | ふれんずが振る |
| レインズ物件番号 | `400139534044` | レインズが振る |
| AMS物件番号 | `000002503387` 等 | **自社がAMS登録順に振る（自社内でのみ意味を持つ）** |

**AMSの番号は自社の登録順の通し番号であり、ふれんず番号ともレインズ番号とも対応しない。**
→ 番号だけで機械的に「ふれんずのこの物件＝AMSのこの物件」と繋ぐことは原理的にできない。

### 営業は実務で「物件の実体」で照合している
番号で繋がらないため、営業は所在地・面積で同一物件かを判断している。
システムも同じことを行う（人手照合を、システムが助ける）。

### 照合の主鍵
**「所在地（丁目レベル）＋ 面積（小数点以下まで）」を主鍵とする。**

- 面積は登録時から基本的に変わらない（価格や状態と違い、動かない）→ 鍵として安定。
- 面積は小数点以下まで（例 `80.79㎡`）あり精度が高い → 識別子として機能する。
- 所在地（丁目）でさらに大きく絞れる。
- 「所在地（丁目）＋ 面積（小数点以下）」の組み合わせで、**99%は同一物件と判定してよい。**
- ただし各社の記載差で面積が微妙にずれることがあるため、**近似幅を設けて吸収する**
  （幅の具体値は実データ〔CSVとAMSの同一物件の面積差〕を見てから決定。構造は幅に依存しない）。
- 価格・種目は補強材料として使う（照合の主鍵ではなく、確度を上げる補助）。
  ※価格は「同一物件かを見る手がかり」と「同一物件確定後の“変更検出対象”」の二面を持つので扱いを分ける。

## 3. 照合MCPサーバーのロジック（背骨）

```
ふれんず物件（CSV1行）が来る
  ↓
① 対応表に、この物件番号の対応が既にあるか？
   ある → AMS物件番号で確定（近似照合は不要・速く確実）
   ない → ②へ
  ↓
② 所在地（丁目）＋ 面積（近似幅つき）で、AMS側を検索
  ↓
③ 候補件数で分岐（IF文＝条件分岐）
   ・1件   → 自動結合（同一物件と判定）
   ・複数件 → 無理に照合しない。営業に候補を提示 →
              営業が選ぶ → 確定 → 対応表に記録（次回から①で番号一致）
   ・0件   → AMS未登録候補として営業に提示（新規物件の漏れの可能性）
  ↓
④ 確定したペアで、価格・状態の食い違いを検出（本来の目的）
  ↓
⑤ 物件の旗（状態）を見る／立てる（→ 第4章）
```

- **各機能はMCPサーバーとして個別に作る**（プラガブル／1機能1部品）。
  n8n がこれらを組み合わせてフローを回す。1つを直しても他に影響しない。
- ③の3分岐は数学的に「0件／1件／複数件」で必ず尽きる。3つとも設計に含める
  （後から「0件のとき」で手戻りしないため）。

### 対応表（人間の判断の蓄積）
- 営業が複数候補から選んで確定した「ふれんず物件番号 ⇔ AMS物件番号」の対応を記録する。
- 次回以降、その物件は①で番号一致し、近似照合が不要になる。
- 使うほど対応表が育ち、照合が速く確実になる＝**会社固有の知能**（他社には無い蓄積）。
- 対応表は「AMS本体を書き換える」ものではなく、システム側に持つ別の記録。
  → 大原則「AMSに書き戻さない／検知・通知のみ」を守る。

## 4. 旗（状態管理）とタイムラグ（重要）

### なぜ旗が必要か
営業が確認・判断しても、**AMS本体がすぐ最新になるとは限らない。**

```
営業が確認・判断
  → 営業サポートへAMS更新を依頼
    → 営業サポートがAMSを手動更新
（この間にタイムラグ。営業サポートが休みならさらに遅れる。手動なので入力ミスもありうる）
```

**「営業が確認した時点」と「AMS本体が最新になった時点」は一致しない。**
これを無視すると、システムは確認済みの食い違いを毎回“新しい問題”として蒸し返し、
営業を無駄に煩わせ、信頼されなくなる（うるさくて使われない）。

### 3つの時点を区別する
| 時点 | 内容 |
| ---- | ---- |
| ふれんずの真実 | CSVの情報。最も新しい状態 |
| AMSの現状 | 引き出したデータ。ふれんずより古いことがある（更新待ち） |
| 営業の判断 | 旗。AMSより進んでいることがある（気づいたがAMS未反映） |

### 物件の旗（状態）
| 旗 | 意味 | システムの振る舞い |
| ---- | ---- | ---- |
| 未確認 | まだ誰も確認していない | 食い違いがあれば通知する |
| 確認済み・対応中 | 営業が確認しAMS更新依頼済み。AMS未反映（更新待ち） | 食い違いがあっても**再通知しない**。ただし長期間反映されなければ**督促**する |
| 反映済み | AMSが更新されふれんずと一致 | 旗を下ろす。更新後もまだ食い違う → **入力ミスの可能性**として通知 |

- 各旗に「いつ」を持たせる（確認日・依頼日・反映日）。タイムラグを時間として記録する。
- 「反映済み」判定は、次回照合で「以前食い違っていた物件が一致した」ことをシステムが自動検知する方向が有力（人の手間が少ない）。
- 旗と照合の組み合わせは、**入力ミスの発見**という副次的価値も生む
  （更新したはずなのにまだ食い違う＝ミスの疑い）。
- タイムラグは許容するが、放置は許容しない（督促で拾う）。

### AMSは整えず、旗を被せる（道A/Bの結論）
AMS由来データは「誰も照合していない／ID確定済み／新規漏れ／消失」など、
それ自体が確認・更新の途中にある“動いているデータ”である。これをどう扱うか2案あった。

- 道A: AMSデータ自体を整えてから照合する（重い・AMS書き換えに近く危険）
- 道B: 自動取得したAMSデータと照合するだけにする（簡単）

**結論：道Bから始める。** 森の指摘する4状態（未照合・ID確定・新規漏れ・消失）は、
AMSデータ本体を整える（道A）のではなく、**既に設計した「旗」と「対応表」で外側から管理する。**

- AMSデータは自動取得したものをそのまま照合の相手にする。
- その上に「旗（状態の付箋）」を貼る。AMS本体（本）は書き換えない。付箋は貼り替え・剥がしができる。
- これは大原則「AMSに書き戻さない」と一致する。
- 各機能を部品化（MCPサーバー）しているため、将来「AMSデータを整える必要がある」と
  実データで分かれば、「AMSデータを取得する部品」だけ後から差し替えられる（道Aへ移行可能）。
- 「来ていない負荷に器を先に作らない」に従い、いま見えていない完璧な参照管理は先に作らない。

## 5. 出口（営業へのメール）

照合の結果、営業本人のメールに以下を届ける。**まずはここまでで完成とする。**

1. **どの物件か** — AMS物件ID ＋ 物件種目（これでDB上ユニークに特定できる）
2. **何が変わったか** — 価格変更／状態変更（商談中・書面による購入申込みあり等）／消失 など
3. **確認への導線** — ふれんずのページURLを持たせ、営業がクリックして現物を確認できる

- システムは「変わったかもしれない」と気づかせるだけ。最終確認は営業が本物のふれんずページで行う
  （「システムは確定でなく、人に気づかせる」）。

## 6. システムが立てる「旗」の全体像

システムは確定でなく、人に気づかせるために旗を立てる。

1. **状態の食い違い** … AMS公開なのにふれんずで商談中／消失 等（旧方式で検出実証済み）
2. **価格変更の可能性** … 複数掲載での価格ばらつき、更新日の新しい掲載での価格差
   （正確な価格取得が前提。数値化＝万/億正規化の作業はこのため）
3. **近似物件の疑い** … 同一物件が別物件として重複登録されている疑い
   （所在地＋面積の一致度で検出）。本方式では③の照合ロジックそのものと同根。
4. **確認の網羅性** … どのCSVにも出てこないAMS物件＝誰も最近確認していない物件を洗い出す

いずれも「人に気づかせる」ためであり、システムが確定・自動更新するものではない。

## 7. 業務上の前提知識（設計の背景・記録）

- **専任媒介**: ふれんずに1社だけが掲載。**一般媒介**: 複数社が同一物件を別々に掲載。
- 一般媒介では更新が各社任せのため情報が食い違う（A社1100万のまま／B社が値下げ更新）。
  システムで一元管理されないことによる必然。→ この食い違い検出こそ本システムの価値。
- 同一物件に複数情報源がある場合、**更新日が新しいものを正とし、古いものは更新遅れとみなす**
  （履歴と更新日で判断）。
- freins_id（旧方式で観測）の重複は、**土地の区画分割（切り売り）や一般媒介の実態**であり
  バグではない。1つのふれんず掲載に対しAMSが区画ごとに複数登録するために起きる。
- 近似物件判定・照合は**AIを使わずルールベースで行う**（費用をかけたくない会社であるため）。
  完璧な自動判定は目指さず、疑わしいものを人に気づかせる。

## 付録：CSVから取得できる主な項目（実データで確認済み・2026-07-03）

ふれんずCSV（Shift-JIS、1行1物件、最大200件）の主なカラム:

物件番号 / 登録日 / 会員商号 / 会員電話番号 / 種目 / 新築中古区分 /
所在地コード / 所在地名１ / 所在地２ / 番地 / 建物名 / 部屋番号 /
最寄沿線・駅・徒歩 / 学区 / **価格** / 土地面積 / 建物専有面積 /
バルコニー面積・方向 / 建物構造 / 階層 / 築年月 / 間取り / 用途地域 /
現況 / 引渡し時期 / 接道 / 駐車場 / 取引態様 / 報酬形態 / 成約日 / 成約価格 …

照合に主に使う: **物件番号・所在地名１・所在地２・番地・土地面積・建物専有面積・価格・種目・登録日・取引態様**
